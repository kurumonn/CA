# 01 要件定義 — 学習用私設CA「PKI Lab」

## 1. 目的

学習者が、次の問いに**実験結果を根拠に**答えられる状態にする。

1. 誰が証明書を発行したか
2. 誰がそのCAを信頼すると決めたか
3. 証明書の何を検証したか
4. 失効した証明書を、どの情報で拒否したか

信頼の起点（トラストアンカー）は検証する側が指定する（RFC 5280）。自己署名が正しく検証できても、そのルートが自動的に信頼されるわけではない。

## 2. 対象範囲

| 項目 | 要件 |
|---|---|
| 利用者 | 自分自身（役割を切り替えて操作する） |
| 発行対象 | 自分が管理するローカル HTTPS サーバー |
| 許可する名前 | `localhost`、`127.0.0.1`（完全一致） |
| CA 構成 | ルートCA＋中間CAの2段、証明書は3階層 |
| 管理方法 | ローカル CLI（`lab/pkilab.py`） |
| 失効方式 | 署名付き CRL |
| 検証方法 | `openssl verify` と、厳格設定の Python TLS クライアントによる実接続 |
| 運用機能 | 承認、台帳、排他、監査、照合、バックアップ、復旧 |
| 教材連携 | 秘密情報を含まないイベント JSON の出力（`export-events`） |

**対象外**：公開ドメイン・公開IP・ワイルドカード・コード署名・第三者への発行・他人の通信の復号。
**追加設計扱い（未実装）**：OCSP レスポンダー、ACME、クライアント証明書、HSM、Web 管理画面、HTTPでのCRL取得・伝播の統合検証（配布用HTTPサーバー自体は存在）。

## 3. 役割と権限

| 役割（`--role`） | 許可する操作 | 持たせない権限 |
|---|---|---|
| `server-admin` | 鍵生成・CSR 作成・申請、HTTPS 起動 | CA 秘密鍵の利用 |
| `ra` | 審査・承認・却下 | CA 署名 |
| `issuer` | 承認済み証明書の発行、葉の失効、中間CA CRL、復旧照合 | ルート鍵の利用 |
| `root-admin` | ルート作成、中間CAへの署名・失効、ルート CRL | 日常的な葉の発行 |
| `verifier` | 検証用バンドル、証明書検証、TLS 接続試験 | 暗黙の信頼追加 |
| `auditor` | 監査ログ検証、照合、イベント出力、確認付き再アンカー | 無条件の記録改変 |
| `operator` | バックアップ・復元・再開承認・公開物配布・状態表示 | 署名 |

役割は `lab/pkilab.py` の `ROLE_OPS` で強制する。ただし1人がアカウントを切り替えるだけでは独立した二者承認・独立監査にはならない（申請者と承認者が同じ場合は承認記録に `requester_and_approver_same_actor` を残す）。

## 4. 機能要件

| ID | 機能 | 完成条件 | 実装 |
|---|---|---|---|
| FR-01 | CA 鍵の分離 | ルートと中間が別鍵。発行領域にルート秘密鍵がない | `root/` と `issuer/` を分離 |
| FR-02 | 利用側での鍵生成 | サーバー秘密鍵を CA に提出しない | `request` が `server/private/` に生成 |
| FR-03 | CSR 検証 | 不正署名・許可外の鍵・過大入力を拒否 | `inspect_csr()` |
| FR-04 | 発行内容の審査 | 許可外 SAN・CA 権限要求を拒否 | `check_san_policy()`、禁止拡張検査 |
| FR-05 | 承認管理 | 承認を CSR・プロファイル・SAN・期間・承認者・期限に結び付ける | `approvals/<REQ>.json` |
| FR-06 | 証明書発行 | 発行後検査と台帳登録まで完了 | `cmd_issue()` |
| FR-07 | 証明書検証 | 信頼・名前・用途・期限・署名・制約を確認 | `cmd_verify()` |
| FR-08 | 葉の失効 | 中間CA CRL で拒否される | `revoke` |
| FR-09 | 中間CAの失効 | ルート CRL で配下が拒否される | `revoke-intermediate` |
| FR-10 | CRL 運用 | 生成・配布・鮮度確認 | `crl-root` / `crl-issuer` / `serve-public` |
| FR-11 | 更新・世代交代 | 親の残存期間不足を検出して停止。失効した中間CAは発行を止め、新しい鍵の世代へ移る | `ISSUER_RENEWAL_REQUIRED`、CA 状態、`init-issuer --new-generation` |
| FR-12 | 監査・復旧 | 監査異常で凍結し正常化しない、内容まで照合、改ざん検出付きバックアップ、新しさ・鍵の準備を分けて判定し保留から再開 | `audit-verify` / `audit-reanchor` / `check` / `backup` / `restore` / `resume` |
| FR-13 | 排他・再実行制御 | 同時更新・二重発行・監査ログの競合を防ぎ、署名済み証明書を一意に追跡して復旧する | CA・監査ロック、冪等な `issue`、`recover` |
| FR-14 | 教材用出力 | 秘密情報を出さず、観測した粒度のまま（未実施の段階を実測として出さない）処理結果を可視化 | `export-events` → `viz/` |

## 5. 非機能要件（ラボ向けの選定値）

| 項目 | 設計値 |
|---|---|
| HTTPS 待受 | `127.0.0.1:8443`（最低TLS 1.3） |
| 公開物配布 | `127.0.0.1:8000`、読み取り専用、`public/` のみ |
| 発行 API | ネットワークに公開しない |
| 想定規模 | 1CAあたり最大1,000件 |
| CSR 上限 / CRL 上限 | 64 KiB / 1 MiB |
| 同時更新 | 同一CAにつき1処理（`flock`） |
| 発行処理時間 | 10秒以内を設計目標とする（承認待ち・鍵解除を除く）。実機性能保証ではない |
| 判定できないとき | 「判定不能（INDETERMINATE）」と記録し、接続は許可しない |

## 6. 完成の基準

「証明書を発行できた」ではなく、**「不正な発行を止め、失効を検証し、障害後も信頼状態を壊さずに復旧できた」**ことを完成とする。受入試験は `04_acceptance-tests.md`。


## 7. 完成判定を分ける

構造・監査の整合性、現在の運用可能性、バックアップの新しさ、鍵アクセス、再開承認を別項目にする。外部レビュー未検証項目を「全解決」としない。ローカル、CI、SwiftShader、実GPUの結果を混同しない。Round 4の契約と例外判断は [運用手順](06_operations.md) を参照。
