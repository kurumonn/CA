# 自分だけの認証局（CA）を設計する
## ― 要件定義・基本設計・詳細設計をやさしく解説

前回は、OpenSSL・Python・curl を使って自分だけの認証局（CA）を作り、ローカルの HTTPS 通信で「信頼される／されない」「失効した証明書を拒否できる／できない」を実験しました。

今回はその続きとして、**「CAをちゃんと設計するなら、何を決めておく必要があるのか」**を、システム開発と同じ流れで整理します。

1. **要件定義** … 何のために、どこまで作るか
2. **基本設計** … 全体の構成と、守るべきルール
3. **詳細設計** … ファイル配置、データ、処理手順、異常時の動き

> **この記事の結論**
> CAの完成条件は「証明書を発行できた」ではありません。
> **「不正な発行を止め、失効を検証でき、障害が起きても信頼状態を壊さずに復旧できる」**ことです。

## 1. はじめに：前回の実験で分かったこと

前回の実験結果をおさらいします。

| 検証内容 | 結果 |
|---|---|
| 自作CAによる証明書発行 | 成功 |
| 正しいルートCAでの証明書検証 | 成功 |
| ルートCAを信頼させないHTTPS接続 | 失敗（期待どおり） |
| 接続先ホスト名が異なる証明書 | 拒否（期待どおり） |
| 証明書の失効とCRL生成 | 成功 |
| CRLを使用した失効証明書の検証 | 拒否（期待どおり） |

ここから分かる大事なことは2つです。

**① 証明書を「発行できる」ことと、「信頼される」ことは別**

誰でも OpenSSL で証明書は作れます。しかし、その証明書を信頼するかどうかを決めるのは**検証する側（ブラウザやOS、curl など）**です。RFC 5280 でも、信頼の起点（トラストアンカー）は検証者側が持つものとして扱われています。

**② CAで失効させても、利用側が確認しなければ接続できてしまう**

CAが「この証明書はもう使わないで」と CRL（失効リスト）に載せても、curl のように**既定では失効確認をしないクライアント**は、そのまま接続できてしまいます。失効は「CAが登録する」「情報を配る」「利用側が確認する」の3つがそろって初めて機能します。

この2点を前提に、学習用CAを「設計」していきます。

## 2. 前回のキットから改善する3つのポイント

前回のキットは「まず動かして体験する」ためのものでした。設計の観点で見直すと、次の3点が不十分です。

| 問題点 | なぜ不十分か | 今回の設計 |
|---|---|---|
| ルートCAと中間CAの鍵が同じPCにある | 片方が漏れると両方が危険。オフラインルートの運用を学べない | ルート専用VMを分け、普段は停止しておく |
| 発行できれば完成としていた | 誤発行・同時実行・途中停止・台帳消失に対応できない | 審査・承認・排他・監査・復旧を要件にする |
| CRLを作っただけで失効対応済みとしていた | 配布されない・古い・検証されないCRLは役に立たない | 配布・鮮度確認・チェーン全体の検証までを1セットにする |

> **補足：openssl ca は本番用ではありません**
> OpenSSL の公式ドキュメント自身が、`openssl ca` コマンドは本格的な CA の実装ではなく、データベースのロック（排他制御）も行わないと注意しています。今回の設計は、この制約を理解したうえでの「学習用」です。

## 3. 要件定義 ―「何のために、どこまで作るか」

### 3-1. 目的

学習者が、次の4つの問いに**実験結果を根拠に答えられる**ことを目標にします。

- **誰が**証明書を発行したのか
- **誰が**そのCAを信頼すると決めたのか
- 証明書の**何を**検証したのか
- 失効した証明書を**どの情報で**拒否したのか

### 3-2. 対象範囲

| 項目 | 今回の範囲 |
|---|---|
| 利用者 | 自分自身（役割を切り替えて操作） |
| 発行対象 | 自分が管理するローカル HTTPS サーバー |
| 許可する名前 | `localhost`、`127.0.0.1` のみ |
| CA構成 | ルートCA＋中間CAの2段（証明書はルート→中間→サーバーの3階層） |
| 管理方法 | ローカルのコマンド操作（CLI） |
| 失効方式 | 署名付き CRL |
| 検証方法 | OpenSSL による証明書検証＋専用クライアントによる実TLS接続 |
| 運用機能 | 承認、台帳、更新、監査、バックアップ、復旧 |
| 教材連携 | 秘密情報を含まないイベントJSONの書き出し（3Dアニメ用） |

**対象外**：公開ドメイン、公開IP、ワイルドカード、コード署名、第三者への発行、他人の通信の復号。
**将来の追加設計**：OCSP、ACME、クライアント証明書、HSM、Web管理画面。

「やらないこと」を最初に決めるのも、要件定義の大切な仕事です。

### 3-3. 役割と権限 ―「受付」と「署名」を分ける

CAの仕事は、銀行の窓口にたとえると分かりやすくなります。

- **窓口係（RA：登録局）** … 申込書の内容と、申込者にその権利があるかを確認する
- **印鑑を押す人（CA）** … 承認済みのものにだけ署名する
- **お客さん（利用者・検証者）** … 受け取った書類を、自分の基準で確認する

| 役割 | できること | 持たせない権限 |
|---|---|---|
| サーバー管理者 | サーバー鍵の生成、CSR作成、証明書の配置 | CA秘密鍵の利用 |
| RA担当 | 申請内容・対象への権限の確認、承認 | CA署名 |
| 中間CA担当 | 承認済み証明書の発行、失効、CRL生成 | ルート鍵の利用 |
| ルートCA管理者 | 中間CAの発行・失効、ルートCRL生成 | 日常的なサーバー証明書の発行 |
| 検証者 | 信頼設定、証明書・TLS検証 | 勝手な信頼の追加 |
| 監査担当 | 台帳・承認・操作記録の照合 | 記録の変更 |

> **注意**：1人がアカウントを切り替えるだけでは、本当の意味の「二者承認」や「独立監査」にはなりません。今回は**役割分離の考え方を学ぶ**ための構成です。

### 3-4. 機能要件

| ID | 機能 | 完成条件 |
|---|---|---|
| FR-01 | CA鍵の分離 | ルートと中間が別鍵。発行環境にルート秘密鍵がない |
| FR-02 | 利用側での鍵生成 | サーバー秘密鍵をCAへ渡さない |
| FR-03 | CSR検証 | 不正な署名・許可外の鍵・大きすぎる入力を拒否 |
| FR-04 | 発行内容の審査 | 許可外のSANやCA権限の要求を拒否 |
| FR-05 | 承認管理 | 承認をCSR・プロファイル・期間に紐づける |
| FR-06 | 証明書発行 | 署名後の検査と台帳登録まで完了 |
| FR-07 | 証明書検証 | 信頼・名前・用途・期限・署名・制約を確認 |
| FR-08 | サーバー証明書の失効 | 中間CAのCRLで拒否される |
| FR-09 | 中間CAの失効 | ルートCAのCRLで配下が拒否される |
| FR-10 | CRL運用 | 生成・配布・更新・鮮度確認 |
| FR-11 | 更新・世代交代 | 新しい鍵への切替と旧証明書の廃止を追跡 |
| FR-12 | 監査・復旧 | 台帳と記録を照合し、隔離環境で復元 |
| FR-13 | 排他・再実行制御 | 同時更新と二重発行を防ぐ |
| FR-14 | 教材用出力 | 秘密情報を出さずに処理結果を可視化 |

### 3-5. 非機能要件（ラボ用の目安）

以下はこのラボのために決めた値で、公開CAの基準ではありません。

| 項目 | 設計値 |
|---|---|
| HTTPS待受 | `127.0.0.1:8443` |
| 公開物の配布 | `127.0.0.1:8000`（読み取り専用） |
| 発行API | ネットワークに公開しない |
| 想定規模 | 1CAあたり最大1,000件 |
| CSRサイズ上限 | 64 KiB |
| CRLサイズ上限 | 1 MiB |
| 同時更新 | 同じCAにつき1処理だけ |
| 発行処理時間 | 10秒以内（承認待ちなどを除く） |
| 検証処理時間 | 1秒以内 |
| 復旧時間 | 2時間以内 |
| 判断できないとき | 「判定不能」と記録し、**接続は許可しない** |

最後の「判断できないときは止める」は特に重要です。安全側に倒す（フェイルクローズ）という考え方です。

## 4. 基本設計 ―「全体の形と、守るルール」

### 4-1. 全体構成

```
┌───────────────────────────────────┐
│ Root VM（ネットワークなし・普段は停止）│
│   ルートCA秘密鍵                    │
│     ├─ 中間CA証明書に署名           │
│     └─ ルートCRLに署名              │
└──────────────┬────────────────────┘
               │ 持ち込む：CSR・承認記録
               │ 持ち出す：公開証明書・CRL だけ
               ▼
┌───────────────────────────────────┐
│ Lab VM（外部に非公開）               │
│   申請者 → RA → 中間CA              │
│                 ├─ サーバー証明書   │
│                 └─ 中間CA CRL       │
│   HTTPSサーバー（サーバー秘密鍵）    │
│   公開物配布 → 検証クライアント      │
│   匿名化Exporter → 教材イベントJSON │
└───────────────────────────────────┘
```

ポイントは**「ルートCAは普段電源を切っておく」**ことです。ルート秘密鍵は、中間CAに署名するときだけ使い、Lab VMには絶対にコピーしません。

> WSL2 だけで全部を動かす簡易構成も可能ですが、その場合は「論理的に役割を分けた実験」と位置づけ、オフラインルートの安全性を再現したとは考えません。

### 4-2. 証明書が発行されるまでの流れ

```
① サーバー側で秘密鍵を作る（秘密鍵は外に出さない）
② 公開鍵を入れた CSR（証明書署名要求）を作り、秘密鍵で署名
③ RA が CSR と申請内容を確認
④ 承認内容を記録
⑤ 中間CAが証明書に署名
⑥ 発行後の検査・台帳登録・監査記録
⑦ サーバー証明書＋中間CA証明書を返す
⑧ サーバーに配置し、実際に TLS 接続して確認
```

**CSR は「署名付きの申込書」**です。中身は公開鍵や希望する名前で、秘密鍵そのものは入っていません。

そして見落としがちなのが次の点です。

> **CSRの署名が正しい ≠ 申請者にその名前を使う権利がある**
> CSRの署名は「この公開鍵に対応する秘密鍵を持っている」ことしか示しません。「その名前（ドメイン）を管理している」ことの確認は、RAが別の工程で行います。

### 4-3. 証明書プロファイル ―「どの欄に何を書くか」の発行ルール

| 項目 | ルートCA | 中間CA | TLSサーバー |
|---|---|---|---|
| 鍵 | EC P-256 | EC P-256 | EC P-256 |
| 署名 | ECDSA + SHA-256 | ECDSA + SHA-256 | ECDSA + SHA-256 |
| 有効期間 | 1,825日 | 365日 | 30日 |
| Basic Constraints | CA:TRUE, pathlen:1 | CA:TRUE, pathlen:0 | CA:FALSE |
| Key Usage | keyCertSign, cRLSign | keyCertSign, cRLSign | digitalSignature |
| EKU（用途） | 省略 | serverAuth | serverAuth |
| SAN（名前） | なし | なし | localhost, 127.0.0.1 |
| CRL配布先 | なし | ルートCRL | 中間CA CRL |

いくつか用語を補足します。

- **Basic Constraints（基本制約）** … 「この証明書はCAとして他の証明書に署名してよいか」を示します。サーバー証明書は必ず `CA:FALSE` にします。
- **pathlen:0** … 「この下にさらにCAを作ってはいけない」という意味です。**サーバー証明書を発行できない、という意味ではありません。** また、署名そのものを物理的に止める機能でもないため、発行側の審査と検証側のチェックを併用します。
- **SAN（サブジェクト代替名）** … 接続先の名前を照合する欄です。現在のルール（RFC 9525）では、CN（共通名）ではなく **SAN で照合**します。今回の設計でも、CNだけ一致する証明書は受け入れません。
- **Name Constraints（名前制約）** … 中間CAに「`localhost` と `127.0.0.1` 以外の名前は発行させない」という制約を付けます。ただし DNS 名の制約は「その名前の配下」も許してしまう仕組みなので、`sub.localhost` などは発行審査の段階で別途拒否します。

### 4-4. 鍵の管理

| 鍵 | 保管場所 | 守り方 |
|---|---|---|
| ルート秘密鍵 | Root VM | 暗号化PKCS#8、普段は停止、アクセス限定 |
| 中間CA秘密鍵 | Lab VM のCA専用領域 | 暗号化PKCS#8、署名担当だけが使用 |
| サーバー秘密鍵 | サーバー専用領域 | 専用アカウント、所有者のみ読み書き（0600） |
| バックアップ | 別の媒体 | CA鍵とは別のパスワードで暗号化 |

- CA鍵は **PKCS#8 の暗号化形式**（PBES2 / AES-256-CBC / PBKDF2-HMAC-SHA-256）で保存します。反復回数は、実機で解除時間を測って決めます。
- パスフレーズは**コマンドの引数・ソースコード・ログに残さない**ようにします（`ps` コマンドや履歴から見えてしまうため）。
- サーバー秘密鍵だけは、ローカルデモの利便性のために暗号化なしを許容します。ただし「安全な保管方法だから」ではなく「例外として」の扱いです。

### 4-5. 失効の構成

| 失効させるもの | 失効させる人 | 利用側が確認する情報 |
|---|---|---|
| サーバー証明書 | 中間CA | 中間CA CRL |
| 中間CA証明書 | ルートCA | ルートCRL |
| ルート（信頼の起点） | **検証する側の管理者** | 信頼設定から削除 |

ルートCAは「自分自身を失効させる」ことができません。ルートを信頼するのをやめるのは、利用側の仕事です。

OpenSSL では、`-crl_check` はサーバー証明書だけ、`-crl_check_all` はチェーン全体の失効を確認します。**サーバー証明書のCRLだけを渡して「中間CAまで確認した」とはみなしません。**

**CRLの更新方針（ラボ用の値）**

| 項目 | ルートCRL | 中間CA CRL |
|---|---|---|
| 有効期間 | 30日 | 24時間 |
| 定期更新 | 14日以内 | 学習開始時と、継続中は12時間以内 |
| 失効が発生したら | すぐ再発行・配布 | すぐ再発行・配布 |
| 初期状態 | 失効0件のCRLを作成 | 失効0件のCRLを作成 |

CRLが取得できない・期限切れ・署名不正のときは接続を許可しません。ただし記録上は、**「失効している」と「失効状態を確認できない」を別の結果**として残します。

## 5. 詳細設計 ―「具体的にどう作るか」

### 5-1. ファイル配置

```
/srv/pki-lab/
├── config/      CA設定・固定プロファイル
├── requests/    CSR原本・申請情報
├── approvals/   承認記録
├── issuer/
│   ├── private/   中間CA秘密鍵
│   ├── certs/     中間CA証明書
│   ├── db/        発行・失効台帳
│   ├── newcerts/  発行済み証明書
│   ├── crl/       CRL原本
│   └── lock/      排他制御
├── journal/     未完了操作の記録
├── audit/       監査記録
├── server/
│   ├── private/   サーバー秘密鍵
│   └── certs/     サーバー証明書・中間チェーン
├── public/      公開してよい情報だけ
├── verifier/
│   ├── trust/     明示的に信頼したルート
│   └── cache/     検証用CRL
└── exports/     教材用の匿名化JSON
```

`public/` から秘密鍵や台帳が見えないようにします。**CAの作業フォルダをそのままWeb公開するのは厳禁**です。

### 5-2. 保存するデータ

| データ | 主な項目 |
|---|---|
| 申請 | 申請ID、申請者、資産ID、CSRハッシュ、公開鍵ハッシュ、希望プロファイル |
| 承認 | 承認ID、CSRハッシュ、プロファイルハッシュ、承認SAN、期間、承認者、期限 |
| 証明書 | 発行者ID、シリアル、証明書ハッシュ、有効期間、申請ID |
| 失効 | 発行者ID、シリアル、理由、失効時刻、操作者、インシデントID |
| CRL | 発行者ID、CRL番号、発行時刻、次回更新期限、ハッシュ |
| 操作記録 | 操作ID、開始・終了、入出力ハッシュ、終了値、復旧要否 |
| 監査イベント | 連番、操作者、操作、結果、対象、時刻、前後のハッシュ |

証明書は**「発行者ID＋シリアル番号」の組み合わせ**で識別します。シリアル番号だけでは、別のCAが同じ番号を使う可能性があるためです。

### 5-3. 申請の状態遷移

```
RECEIVED（受付）
   ↓
VALIDATED（形式チェック済み）
   ↓
APPROVED（承認）
   ↓
SIGNING（署名中）
   ↓
ISSUED（発行済み）
   ↓
PUBLISHED（公開済み）
```

例外の状態もあらかじめ決めておきます。

| 状況 | 状態 |
|---|---|
| 審査で不合格 | REJECTED |
| 承認の期限切れ | APPROVAL_EXPIRED |
| 署名できたか分からない | NEEDS_RECOVERY |
| 発行後の検査で不合格 | QUARANTINED（隔離） |

**途中で止まった申請を、確認せずにもう一度署名してはいけません。**すでに署名済みの可能性があるため、台帳・発行物・操作記録を照合してから再開します。

### 5-4. CSR受付時の検査

サイズ、形式、CSRの署名、鍵の種類、要求された名前（SAN）、要求された用途をチェックします。

`CA:TRUE` や `keyCertSign`、`clientAuth` など、サーバー証明書に不要な権限を求めるCSRは拒否します。さらに、**CSRに書かれた拡張は信用せず、CA側で決めたプロファイルから作り直します。**

```ini
copy_extensions = none
```

OpenSSL の公式ドキュメントも、CSRの拡張を不用意にコピーすると、**申請者にCA証明書を渡してしまう危険**があると説明しています。

承認は次の内容にまとめて紐づけ、どれか1つでも変わったら再承認に戻します。

```
CSRのハッシュ ＋ プロファイルのハッシュ ＋ 承認したSAN
＋ 承認した有効期間 ＋ 承認者 ＋ 承認期限
```

### 5-5. 有効期間の決め方

子の証明書が親CAより長生きしないようにします。

```
notBefore = max(現在時刻 - 300秒, 発行元CAのnotBefore)
notAfter  = 現在時刻 + プロファイルの標準期間

必須条件：notAfter <= 発行元CAのnotAfter - 24時間
```

条件を満たせないときは、勝手に期間を短くせず `ISSUER_RENEWAL_REQUIRED`（親CAの更新が必要）で止まります。

期限切れの実験のために OS の時刻をいじることはしません。期限切れ用の試験証明書や、OpenSSLの評価時刻指定（`-attime`）で再現します。

### 5-6. 発行処理と排他制御

```
CA単位のロックを取得
   ↓
承認・CSR・設定・CAの状態を再確認
   ↓
「操作開始」を記録（途中で止まっても分かるように）
   ↓
非公開の場所に証明書を生成
   ↓
証明書・台帳・newcerts を照合
   ↓
構造・鍵の一致・チェーン・用途・期間を検査
   ↓
監査記録とバックアップ
   ↓
公開領域へ切り替え
   ↓
「完了」を記録
   ↓
ロック解放
```

発行・失効・CRL生成・台帳更新は、同じCAなら**同じロック**を使います。ただしロックがあっても複数ファイルの更新が「全部成功か全部失敗か」になるわけではないため、途中停止後の整合性確認も用意します。

同じ申請IDを再実行した場合、完了済みなら**元の証明書を返すだけ**にします（二重発行の防止）。

### 5-7. OpenSSL設定の要点

サーバー証明書の拡張設定です。

```ini
[ server_localhost ]
basicConstraints       = critical, CA:FALSE
keyUsage               = critical, digitalSignature
extendedKeyUsage       = serverAuth
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always
subjectAltName         = DNS:localhost, IP:127.0.0.1
```

CRLの拡張は、定義するだけでなく CA 設定から参照させます。

```ini
[ CA_default ]
copy_extensions = none
crl_extensions  = crl_ext

[ crl_ext ]
authorityKeyIdentifier = keyid:always
```

中間CAの名前制約は、たとえば次のように書きます（IPはアドレスとサブネットマスクで指定します）。

```ini
nameConstraints = critical, permitted;DNS:localhost, permitted;IP:127.0.0.1/255.255.255.255
```

> 設定ファイルだけでは、承認・排他・バックアップ・復旧は実現できません。これらは周辺のスクリプトで作り込む部分です。

### 5-8. 証明書とCRLの検証

公開情報だけを集めた「検証用バンドル」を作ります。

```
validation-bundle/
├── root.cert.pem          信頼するルート
├── intermediate.cert.pem  中間CA
├── server.cert.pem        サーバー証明書
└── crls.pem               ルートCRL＋中間CA CRL
```

```bash
openssl verify \
  -show_chain -x509_strict -auth_level 2 -verify_depth 1 \
  -purpose sslserver -verify_hostname localhost \
  -trusted root.cert.pem \
  -untrusted intermediate.cert.pem \
  -CRLfile crls.pem -crl_check -crl_check_all \
  server.cert.pem
```

| 結果 | 表示例 |
|---|---|
| 正常 | `server.cert.pem: OK` |
| 失効 | `certificate revoked` |
| CRLがない | `unable to get certificate CRL` |
| CRLが古い | `CRL has expired` |

- `-trusted` には**信頼するルート**、`-untrusted` には**経路を組み立てるための中間CA**を渡します。中間CAを信頼の起点にはしません。
- 終了コードだけでなく、**想定した理由で拒否されたか**まで確認します。
- `openssl verify -verify_hostname` は、**接続先と同じ種類の SAN が無いと CN を見に行きます**。「SAN が何か入っている」だけでは防げません（たとえば CN=localhost・SAN が IP:127.0.0.1 だけの証明書は、localhost として通ってしまいます）。そこで、DNS 名で接続するなら DNS 型、IP なら IP 型の SAN が**完全一致**で含まれることを事前に確認します。

### 5-9. 実際のTLS接続での検証

ファイルの検証に成功しても、実際の接続で同じ条件が使われているとは限りません。前回の実験で、**curl は既定で CRL を確認しないため、失効済みでも接続できてしまう**ことを確認しました。

そこで専用クライアント（Python の `ssl.SSLContext`）で、1つの接続の中で次をすべて有効にします。

- 証明書を必須にする（`CERT_REQUIRED`）
- ホスト名を検証する（`check_hostname = True`）
- CN へのフォールバックを無効にする（`hostname_checks_common_name = False`）
- 厳格な X.509 検証（`VERIFY_X509_STRICT`）
- チェーン全体の CRL 確認（`VERIFY_CRL_CHECK_CHAIN`）

参考までに curl でも `--crlfile` で CRL を指定できます（パスは後述のラボの配置）。

```bash
curl --noproxy '*' \
  --cacert lab/work/public/certs/root.cert.pem \
  --crlfile lab/work/public/crl/intermediate.crl.pem \
  https://localhost:8443/
# → curl: (60) SSL certificate problem: certificate revoked
```

> **CAは通信を暗号化・復号する存在ではありません。**
> TLS 1.3 では、サーバーは自分の秘密鍵でハンドシェイクに署名（CertificateVerify）し、「証明書の持ち主本人であること」を示します。通信の暗号鍵はクライアントとサーバーの間で毎回作られ、CAは関与しません。

### 5-10. ログと監査

発行の成功だけでなく、受付・審査・拒否・署名・失効・CRL更新・配布・検証・バックアップ・復旧をすべて記録します。

監査では、次のつながりが矛盾していないかを照合します。

```
承認された申請 ⇔ 発行台帳 ⇔ 実際の証明書 ⇔ 失効記録 ⇔ 公開したCRL
```

- ログに**秘密鍵・パスフレーズ・TLSセッション鍵は残さない**。
- 改ざん検出のためにハッシュ連鎖を使いますが、同じPCに置くだけでは全部書き換えられてしまいます。**最後のハッシュと連番は別の媒体にも保存**します。

### 5-11. バックアップと復旧

秘密鍵だけ保存しても、CAは復旧できません。CA証明書・暗号化鍵・台帳・発行済み証明書・失効情報・CRL番号・承認・監査・設定を**一式で**保存します。

**やってはいけない例**：台帳が壊れたので空の `index.txt` を作って、以前のCA鍵で発行を再開する。

これをすると、過去に失効させた証明書の情報が消え、**失効した証明書が「有効」に戻ってしまいます**。状態を確定できないときは、旧CAを廃止して新しい世代に移行します。

### 5-12. 鍵が漏れたときの対応

| 漏れた鍵 | 対応 |
|---|---|
| サーバー秘密鍵 | サーバー停止 → 証明書失効 → 中間CRL更新 → 新しい鍵で再発行 |
| 中間CA秘密鍵 | 発行停止 → ルートで中間CAを失効 → ルートCRL更新 → 新しい中間CAへ移行 |
| ルート秘密鍵 | 旧階層を停止 → 利用側で旧ルートの信頼を削除 → 新ルートを**別経路で**配布 |

## 5.5 実際に動かしてみる

この設計は GitHub で実装・公開しています。Python（標準ライブラリのみ）と OpenSSL 3.x があれば、Linux / WSL2 / macOS で動きます。

- リポジトリ：`https://github.com/kurumonn/CA`
- 実装：`lab/pkilab.py`（審査・承認・排他・失効・検証・監査・復旧を担当し、証明書処理は OpenSSL に任せます）
- 自動テスト：53件（正常系・異常系・各段階でのクラッシュ復旧・監査改ざん後の凍結・同時書き込み・バックアップの巻き戻り検出・実TLS接続を含む）

### 一括デモ

```bash
git clone https://github.com/kurumonn/CA.git
cd CA
bash lab/scripts/demo.sh
```

| 手順 | 確認できること |
|---|---|
| 1 | ルートCAと中間CAを作成（鍵は別ディレクトリ・暗号化） |
| 2〜3 | 申請 → RA審査。`example.com` の申請は `SAN_NOT_ALLOWED` で拒否 |
| 4 | 中間CAが発行（発行後検査・台帳・監査まで） |
| 5 | `verify` で `OK`、`--host example.com` なら `SAN_MISMATCH` |
| 6 | HTTPSサーバーに TLS 1.3 で接続成功 |
| 7〜8 | 失効後、厳格クライアントは `REVOKED` で拒否。**失効確認なしのクライアントと curl の既定動作は接続できてしまう** |
| 9 | 監査ログのハッシュ連鎖と、台帳・CRLの照合がOK |
| 10 | 3Dアニメ用のイベントJSONを出力（秘密情報なし） |

### 1つずつ操作する

役割ごとに許可された操作だけができるようになっています（例：RA の役割では発行できません）。

```bash
cd lab
python3 pkilab.py init                      # ルートCA・中間CA・CRLを作成
python3 pkilab.py request                   # サーバー管理者：鍵とCSRを作って申請
python3 pkilab.py approve REQ-xxxxxxxx-xxxxxxxx   # RA：審査・承認
python3 pkilab.py issue   REQ-xxxxxxxx-xxxxxxxx   # 中間CA：発行
python3 pkilab.py verify --request REQ-xxxxxxxx-xxxxxxxx
python3 pkilab.py serve-https REQ-xxxxxxxx-xxxxxxxx   # 別ターミナルで
python3 pkilab.py client                    # 厳格なTLSクライアントで接続
python3 pkilab.py revoke  REQ-xxxxxxxx-xxxxxxxx --reason keyCompromise
python3 pkilab.py client                    # → REVOKED
python3 pkilab.py client --no-crl           # → 接続できてしまう（比較用）
python3 pkilab.py check                     # 台帳・CRL・監査の照合
```

結果は JSON で返り、拒否のときは理由コードが付きます。

| 結果コード | 意味 |
|---|---|
| `OK` | すべての確認に合格 |
| `UNTRUSTED_ANCHOR` | 信頼ストアのルートまでたどれない |
| `SAN_MISMATCH` | 接続先名が SAN に含まれない |
| `CERT_EXPIRED` | 有効期限切れ |
| `WRONG_EKU` | 用途が違う |
| `LEAF_REVOKED` / `INTERMEDIATE_REVOKED` | 葉／中間CAが失効（証明書ファイルの検証） |
| `REVOKED` | 実際の TLS 接続で失効を検出（葉か中間かは同じ接続では確定できないので、推定は参考情報として別に出します） |
| `NAME_CONSTRAINT_VIOLATION` | 中間CAの名前制約の外 |
| `CRL_MISSING` / `CRL_EXPIRED` | 失効状態を**確認できない**（判定不能 → 接続しない） |

> 作業ディレクトリ `lab/work/` には秘密鍵が作られます。Git には含めない設定（`.gitignore`）にしてあります。

## 6. 公開CA（Let's Encryptなど）との違い

| 観点 | 今回の学習用CA | 公開Web PKIのCA |
|---|---|---|
| 信頼する人 | 自分が明示した検証環境だけ | OS・ブラウザのルートプログラムに組み込まれ、多数の利用者 |
| 発行審査 | 自分の資産と操作権限を確認 | 規定に沿ったドメイン・IPの管理権限確認 |
| ルール | 学習用の独自ルール | CA/Browser Forum の要件＋各ルートプログラムの要件 |
| 監査 | 自己点検 | 独立した第三者監査 |
| 失効情報 | 実験中だけ提供 | 規程に沿って継続的に提供 |
| 鍵保護 | 暗号化ファイル＋環境分離 | HSM などの要件に沿った保護 |
| 障害の影響 | ラボ内だけ | 多数の利用者・サービス |

### SNSでよく見かける誤解を3つ整理します

**① 「Let's Encrypt は無料だから信頼性が低い」→ 誤り**

Let's Encrypt は主要なOS・ブラウザの信頼ストアに組み込まれた、正式な公開認証局です。無料なのは自動化（ACME）と非営利団体による運営によるもので、検証の基準が緩いわけではありません。なお Let's Encrypt は2025年に OCSP の提供を終了し、失効情報は CRL で提供する方針に移行しています。

**② 「自作CAがあればマイナンバーカードの電子証明書の代わりになる」→ 誤り**

公的個人認証サービス（JPKI）は、法律に基づく本人確認、カードによる鍵の保護、失効管理などの仕組みの上に成り立っています。自作CAで同じ形式の証明書を作れても、**誰も信頼の起点として採用していない**ため、代わりにはなりません。

**③ 「自作CAのルート証明書をOSに登録すれば便利」→ 危険**

ルートをOSに登録すると、そのCAが発行した**あらゆるドメインの証明書**をPC全体が信頼します。ルート鍵が漏れれば、銀行サイトの偽証明書すら信頼されかねません。今回の実験では、`--cacert` のように**その場だけ信頼させる方法**を使い、OSの信頼ストアは書き換えていません。

> 私設CAが無意味なわけではありません。社内やラボなど**信頼する範囲を自分で決められる環境**では役に立ちます。ただし、公開CAと同じ信頼範囲・運用保証を持つわけではありません。

## 7. よくある質問（FAQ）

**Q. なぜルートCAから直接サーバー証明書を発行しないのですか？**
A. ルート鍵を使う回数を減らすためです。日常の発行は中間CAが行い、ルート鍵は普段オフラインにしておけます。中間CAが漏れても、ルートで失効させて作り直せます。

**Q. CRL と OCSP の違いは？**
A. CRL は「失効した証明書の一覧表」をまとめて配る方式、OCSP は「この証明書は大丈夫？」と1件ずつ問い合わせる方式です。今回は CRL を採用し、OCSP は比較展示にとどめています。OCSP の `good` という応答は「失効していない」という意味で、名前や期限などを含めて証明書全体が有効という意味ではありません。

**Q. 証明書の有効期間はなぜ30日と短いのですか？**
A. 短いほど、漏れたときの被害期間が短くなり、更新の自動化も身につきます。公開CAでも有効期間を段階的に短くする流れが進んでいます。

**Q. CNに `localhost` と書けば十分では？**
A. いいえ。現在の TLS の名前照合は SAN を使います。CN だけの証明書は、主要なブラウザで拒否されます。

**Q. この設計で本番のCAを運用できますか？**
A. できません。本人確認、HSM、独立監査、CRLの常時配布、OCSP などは対象外です。あくまで「仕組みを理解するための学習用」です。

## 8. まとめ

- 証明書を**発行できる**ことと、**信頼される**ことは別。信頼の起点は検証する側が決める
- ルートCAはオフライン、日常の発行は中間CA、という**鍵の分離**が基本
- **受付（RA）と署名（CA）を分け**、CSRの拡張はコピーせずプロファイルから作る
- 失効は「登録」「配布」「確認」の3点セット。**確認しないクライアントは失効を見逃す**
- 途中停止・台帳消失・鍵漏えいまで想定して初めて「設計した」と言える

次回の記事では、この発行・検証・失効の流れを **three.js の3Dアニメーション**で可視化する学習空間の設計を紹介します。
